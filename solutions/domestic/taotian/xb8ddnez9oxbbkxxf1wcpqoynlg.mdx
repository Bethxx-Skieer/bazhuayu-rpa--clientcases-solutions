## 一、用户与需求

核心矛盾：差评发现滞后、回复不及时影响转化；差评归因靠人工逐条看；评价内容里的产品缺陷/卖点无人挖掘——归因分类=质量/物流/描述/服务四类，VOC 结论反哺选品/运营/客服全店。

两类客户痛点同源，数据来源不同：

- 未购 SaaS 客户（新卖家/小团队）：手动刷新后台看评价、逐条写回复话术、不挖痛点，全靠手；
- 已购 SaaS 客户（旺店通/聚水潭 ERP 等）：ERP 管订单/发货，评价归因与话术不覆盖，仍要人手动做。

适用客户：有口碑管理需求的淘宝/天猫卖家。千牛后台导出自家评价是商家自有权限的官方动作；前台评价按合理频率只读采集属正常浏览；本方案把评价变成改品与话术依据。

## 三、解决方案

### 3.1 功能概述

为淘宝卖家团队打造的评价口碑与 VOC 分析方案，千牛官方导出评价与「问大家」+ 差评归因 + 话术生成，输出差评响应清单与买家之声月报。

每日定时触发并调度多个工具，调起八爪鱼 RPA（Agent 的工具底座，能耦合多系统、完成自动化任务执行）从千牛后台官方导出评价与「问大家」问答内容（商家自有权限、不模拟登录），智能体做差评归因（质量/物流/描述/服务）、生成合规回复话术与邀评建议，周度聚类输出买家之声月报。每日定时辅助，只推送差评响应清单与 VOC 结论，无异常不打扰。

### 3.4 为何这么设计

要同时回答三个问题：**为什么不能只用 SaaS/API？为什么不能纯靠智能体写代码？为什么 RPA 是执行底座？** 本场景的核心是"定时导评、归因话术、VOC 聚类、挂了有人管"。

#### 1）逐项对比

| 对比维度 | SaaS/API 堆叠（旺店通/聚水潭） | 纯智能体（智能体写代码） | 智能体+自动化工具（RPA 工具底座） |
|-|-|-|-|
| 实现方式 | ERP 给订单背景，评价归因无覆盖 | 能爬能分析，但全要自己接 | 千牛官方导出应用直挂 + 前台只读 |
| 风控合规 | 自有数据合规，评价无工具 | 高频爬评价页触发验证码、设备指纹封锁、账号处罚，且有法律风险 | 千牛官方导出（商家自有权限）+ 前台低频只读，合规稳定 |
| 归因判断 | 靠人工逐条 | 需自写分类模型 | 现成导出直挂、归因即开即用 |
| 使用成本（总拥有成本） | ERP 订阅费 | 代理 IP + 服务器 + 开发维护人力，隐性成本高 | 一份平台订阅跑多流程，单方案边际成本 ≈ 0 |
| 维护人要求 | 低（工具现成） | 规则调整都要开发介入 | 可视化流程，客服自己可调归因分类 |

#### 2）优劣势说明

|  | SaaS/API 堆叠（ERP） | 纯智能体（智能体写代码） | 智能体+自动化工具（RPA 工具底座） |
|-|-|-|-|
| 优势 | 订单背景数据真实 | 无订阅费；    <br />可深度定制归因模型 | 千牛官方导出直挂；    <br />归因/话术即开即用；    <br />非技术人员可维护 |
| 劣势 | 评价归因不覆盖；    <br />判断依赖人工 | 高频爬取有封号与法律风险；    <br />导出与保活全自建 | 本地电脑运行需保持开机；    <br />订阅费；    <br />回评/邀评动作需人工确认 |

#### 3）结论

| 论点 | 说明 |
|-|-|
| 官方链路合规 | 千牛后台导出自家评价是商家自有权限的官方动作——不模拟登录、不批量爬取，长期稳定 |
| 归因有模型 | 差评四类归因（质量/物流/描述/服务）沉淀为 Skills，换人可复用 |
| 话术需确认 | 回评/邀评话术生成后需人工确认再执行——回复动作影响店铺评分 |
| 一个底座跑多流程 | 客户购买 RPA 平台是跑多个流程（选品/竞品/口碑），本方案只是其中一个——平台订阅费被多流程摊薄 |
| 时间 | 客服要的是"差评自动归因出话术"，不是"逐条翻评价" |
